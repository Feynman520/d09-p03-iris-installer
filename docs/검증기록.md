### 5-2. 근본 원인

`lib/zip.mjs`의 `normalizeMtimes()`는 압축 전 모든 파일/폴더의 mtime·atime을 고정 epoch(`2026-01-01T00:00:00Z`)로 맞춰 재현성을 보장하도록 설계돼 있었다(이전 세션에 이미 확인·구현됨). 그런데 두 `codex` zip을 바이트 단위로 직접 비교한 결과, 추출된 내용물과 zip 중앙 디렉터리 메타데이터는 완전히 동일한데도 sha256이 달랐다. 로컬 파일 헤더의 Unix 확장 타임스탬프(extra field, 태그 `0x5455` "UT")를 직접 파싱해 대조하자, `mtime`·`atime` 필드는 두 빌드 모두 동일했지만 **`ctime` 필드만 약 74초 차이**가 났다(빌드 a·b의 실제 실행 간격과 일치).

`fs.utimesSync`(Node)는 Win32 `SetFileTime`을 통해 atime·mtime만 설정할 수 있고 **생성 시각(creation time)은 건드릴 수 없다**. bsdtar(Windows용 libarchive)가 zip 엔트리를 쓸 때 파일의 실제 생성 시각을 `ctime`으로 가져다 UT extra field에 넣는데, npm install/npm ci가 두 빌드에서 서로 다른 실제 시각에 파일을 새로 만들었으므로 이 생성 시각이 그대로 최종 zip 바이트에 새어 들어간 것이다. 순수 다운로드/복사 파트는 파일을 매번 새로 "만들지" 않고(캐시에서 복사) 문제가 드러나지 않았다.

### 5-3. 수정

`lib/zip.mjs`의 `zipDir()`에 `normalizeCreationTimes()`를 추가했다. 기존 `toTarSafePath()`와 같은 방식(환경변수로 경로를 넘겨 PowerShell을 스폰 — 한글·반전각 괄호가 든 경로에서도 안전)으로, 압축 대상 디렉터리 전체(`Get-ChildItem -Recurse -Force`)와 루트 자신의 `CreationTimeUtc`를 같은 고정 epoch으로 강제한 뒤 tar를 실행한다.

```

  수정 전: a=9d41a5dc... b=9a6ce27e... (differ)
  수정 후: a=14fbbeec... b=14fbbeec... (MATCH)
```

## 6. 참고 — 이전 세션에서 해결된 항목(역사적 완결성을 위한 요약)

- **tar.exe 8.3 short-path 버그**: Windows `tar.exe`(bsdtar)는 레거시 ANSI 콘솔 앱이라 `GetCommandLineA()`로 명령줄을 받는데, 이 프로젝트 폴더명에 들어간 `〖`/`〗`(U+3016/U+3017)가 이 PC의 cp949 코드페이지로 표현이 안 돼 `?` 바이트로 깨지고 tar가 경로를 못 찾는 문제였다. `lib/zip.mjs`의 `toTarSafePath()`가 PowerShell로 8.3 짧은 경로(예: `P03-IR~1`)를 구해 우회한다(짧은 이름은 `〖`/`〗`를 조용히 생략해 생성되므로 cp949-safe). 짧은 경로 조회는 argv가 아니라 환경변수로 긴 경로를 넘겨 하는데, PowerShell 자체 stdout도 UTF-8로 강제해야 짧은 이름이 돌아올 때 깨지지 않는다.
- **409건 sanitize 히트 remediation**(이전 세션): 벤더 zip 안의 이메일 패턴에 대한 `skipUnder`(`node_modules/`, `node-v24.17.0-win-x64.zip!`, `MinGit-2.54.0-64-bit.zip!`), dash의 계정 이메일·개발 PC 경로 문구에 대한 `redact`, face의 `node_modules`·`state`·`docs`·`_archive`·`.git`·`.playwright-mcp`·`AGENTS.md`·`CLAUDE.md`·`scripts` 제외 목록, `teamclaude-manage.ps1`의 "로컬 쿼터 복구 가드" 블록 제거로 전부 0건까지 해소됐다(이번 0회차 빌드에서 재확인).

## 12. 재검토 후속 — 낡은 PID 신원 불명은 "우리 것 아님" (2026-09-12)

**배경:** 11절 수정 파도를 재검토한 결과 **I6에 잔여 구멍 1개**가 남아 있었다. `bootstrap.ps1`이 낡은 PID의 실행 파일 경로(`$staleProc.Path`)를 읽지 못하면(권한이 없는 프로세스, 마침 종료 중인 프로세스) `$stalePath`가 비고, 경로 비교 블록을 건너뛴 채 `$isOurs`가 **이름 검사 결과 그대로** 남았다. 즉 **경로를 못 읽는 남의 `node.exe`는 여전히 이름만으로 종료**됐다 — IRIS 전역 규칙(이름 기반 일괄 종료 금지)이 정확히 막으려는 행위다.

**고친 방식(판정대로):** 신원 불명 = 우리 것 아님.

- `$isOurs = $false`로 시작한다. 참이 될 수 있는 유일한 길은 `이름이 node` **그리고** `경로를 읽었음`일 때의 `$isOurs = ($stalePath -eq $nodeExe)` 한 줄뿐이다.
- 경로를 못 읽으면 `stale pid <번호>: identity unknown, not stopping.`을 로그에 남기고 **아무것도 종료하지 않는다.**
- 낡은 pid 파일은 어느 경우든 지우고 새 서버를 띄운다. "우리 서버가 아직 살아서 답하는" 경우는 이 단계 **앞**의 헬스 프로브가 이미 처리해 재사용·종료한다(중복 기동 없음).
- ASCII 전용·CRLF 전용 유지. PowerShell 5.1 문법.

**작업 중 잡은 실수 1건:** 새 로그 줄을 `"stale pid $stalePid: identity unknown..."`으로 썼더니 PowerShell이 `$stalePid:`를 **드라이브 한정 변수 참조**로 읽어 파일 전체가 파싱 실패했다(`[System.Management.Automation.Language.Parser]::ParseFile`이 잡아냄). `${stalePid}`로 감싸 해결. 파서 검사를 돌리지 않았다면 설치기가 어느 PC에서도 시작하지 못했을 종류의 오타다.

**행동 확인(실제 프로세스 대상, 아무것도 종료하지 않음):** 같은 게이트 로직을 스크래치 스크립트로 떼어 살아 있는 프로세스에 적용해 판정만 관찰했다(`Get-Process`로 **조회만**, `Stop-Process` 없음).

```
ps1 syntax OK
case A (이 PowerShell, 이름≠node)      : isOurs=False  pathKnown=True
case B (진짜 node, 경로가 동봉본 아님)  : isOurs=False  pathKnown=True
case C (이름=node, 경로 못 읽음)        : isOurs=False  pathKnown=False   ← 이번에 막은 구멍
case D (이름=node, 경로 일치)           : isOurs=True
```

**시험:** `tests/bootstrap.test.mjs`에 2건 추가 — ① `$isOurs`가 거짓으로 시작하고 참이 되는 대입이 경로 비교 **딱 하나**이며 그 비교가 이름·경로 두 조건 안에 있는지, 신원 불명 분기와 로그 문구가 있는지 ② `Stop-Process` 줄이 파일 전체에 하나뿐이고 그것이 `if ($isOurs)` 블록 **안**에만 있는지.

## 6. 알려진 편차 (설계·과제 지시와 다르게 한 것)

1. **S11 행을 `통과`로 적지 않았다.** 과제는 S11(있음)을 행으로 기록하라고 했지만, 그 행이 잡으려는 것은
   「없음」쪽의 `pending` 판정이다. 절반만 확인하고 `통과`로 적으면 게이트가 근거 없이 열린다.

2. **`verify/offline.mjs`를 함께 고쳤다.** 커밋 목록에 없던 파일이지만 ⓐ 3층이 2층의 API 몰이 함수를

3. **고장 주입 9회를 "id마다 새 루트"로 돌린다.** 과제가 허용한 "id마다 루트 재사용"을 택하되,

   아예 발동하지 않기 때문이다(엔진이 `done` 단계를 건너뛰는 지점이 주입 지점보다 앞이다).

   네 단계(`reproduce`·`extract-matrix`·`offline --build`·`offline`·`e2e`)를 하나씩 따로 돌렸다 —

## 7. v2 고치기 1회차 (2026-09-15, 검토 반영)

검토에서 **중요 2건·사소 4건**이 나왔다. 여섯 가지 모두 "돌긴 도는데 무엇을 확인했는지 남지 않거나,
확인이 느슨하다"는 한 갈래였다.

### 7-1. 근거가 실행이 끝나면 사라졌다 (중요)

S08 행의 근거 열은 `_agent\setup\diagnostics.json` 을 가리켰는데, 그 파일은 연습 루트 안에 있고
연습 루트는 실행 끝에 지운다. **가리키는 순간 이미 없는 경로**였다.

고침: 연습 루트를 지우기 **전에** 근거를 `_build\cache\vm\results\S08-<시각>\` 로 옮긴다. VM 경로
(`verify/vm/run.mjs`)가 쓰는 폴더 모양·이름을 그대로 따라 두 경로의 근거가 한 서랍에 쌓인다.

| 파일 | 무엇 |
|---|---|
| `diagnostics.json`·`handoff.json`·`package-receipt.json`·`setup.log`·`installer.log` | VM 경로가 회수하는 다섯과 같은 목록 |
| `설치보고-YYYY-MM-DD.md` | 사람이 읽는 완료 보고 |
| `untouched.json` | 설치 전/후 무접촉 비교표 |
| `verdict.json` | 판정·zip 지문·동봉 판 ↔ 시스템 판·검사 목록 |
| `summary.json`·`summary.txt` | 화면에 찍힌 요약 그대로 |

**`untouched.json` 의 값은 전부 sha256 해시다.** 바탕화면 파일 목록과 `HKCU\Environment` 전문은
이 PC의 사용자 이름·경로를 그대로 담고 있어서 원문으로 남기면 개인정보가 디스크에 굳는다.
"같은가 다른가"만 필요하므로 해시로 충분하고, 해시라서 근거 폴더를 그대로 남에게 보여도 된다.

3층 평소 실행도 같은 이유로 `_build\e2e-results\<시각>\` 에 `summary.json`·`summary.txt` 를 남긴다.

### 7-2. 고장 주입이 "끝까지 갔다"만 보고 있었다 (중요)

재실행 판정이 `percent===100` 뿐이라, **처음부터 전부 다시 돌아도 똑같이 통과**했다. 그러면
「다시 시도 = 실패한 단계부터」(설계-v2 6-4)라는 약속이 지켜지는지 아무도 확인하지 않은 셈이다.

고침: 멈춘 시점과 재실행 뒤의 영수증을 견주어 **모양**을 본다.

- 주입 단계 **앞**: `finishedAt` 이 그대로여야 한다(다시 돌았다면 새 시각이 찍힌다)
- 주입 단계와 **뒤**: `done` 이면서 `finishedAt` 이 달라야 한다(실제로 돌았다는 뜻)

어느 하나라도 어긋나면 실패. 요약표에 「그단계부터」 열이 하나 늘었다.

### 7-3. 나머지 넷

| # | 고침 |

### 2. 시나리오 행은 아직 하나도 못 채웠다

S01~S11 의 VM 행은 전부 `미착수` 그대로다. 마지막 한 걸음에서 막혔다:
**손님 안에서 설치기 사전 점검 ①이 세 건으로 「막힘」** 이 된다.

```text
X 파일 시스템을 확인하지 못했습니다.        (checkNtfs)
X C 드라이브 여유 공간이 3GB 미만입니다.    (checkDisk — 실제 여유 44 GB)
X PowerShell 5.1 이상이 필요합니다.         (checkPowerShell — 실제 5.1 있음)
```

셋의 공통점은 하나뿐이다 — **그 셋만 PowerShell 5.1 을 새로 띄운다.** 같은 화면의
인터넷·기본 브라우저·Edge 검사는 PowerShell 을 안 띄우고 초록이다.

처음엔 PATH 를 의심했지만 실측하니 `--profile` 세션의 PATH 에는 System32 가 이미 들어 있고
`where powershell` 도 찾는다. **진짜 원인은 제한 시간이다.**

```text
installer/lib/precheck.mjs:377   precheck({ timeoutMs = 4000 })
installer/lib/precheck.mjs:380   Promise.all([… checkDisk, checkNtfs, checkPowerShell …])
```

검사 하나당 **4초**인데 PowerShell 을 띄우는 검사 셋이 **동시에** 출발한다. vCPU 2개짜리
갓 설치한 Windows 에서 PowerShell 5.1 냉시동은 하나만도 수 초이고, 셋이 겹치면 4초를 넘긴다.
그러면 세 함수는 `{ok:false}` 로 돌아오고, 화면은 그것을 **원인과 무관한 확정 문구**로 바꾼다:

| 실제로 일어난 일 | 사람이 읽는 문구 |
|---|---|
| `(Get-PSDrive C).Free` 가 4초 안에 안 끝났다 | 「C 드라이브 여유 공간이 3GB 미만입니다」 (실제 44 GB) |
| `(Get-Volume …)` 이 4초 안에 안 끝났다 | 「파일 시스템을 확인하지 못했습니다」 |
| `$PSVersionTable` 이 4초 안에 안 끝났다 | 「PowerShell 5.1 이상이 필요합니다」 (실제 5.1 있음) |

이것은 시험대가 아니라 **설치기의 결함**이다. 사양이 낮거나 바쁜 PC, 백신이 PowerShell
시동을 검사하는 PC에서 **설치기가 거짓 사유로 사람을 완전히 막는다**(사전 점검은 `blockers`
라 진행 자체가 안 된다). 이 PC 본계정은 빨라서 지나가기 때문에 그동안 S08 만 통과해 있었다.
고침 제안 셋(제한 시간 15초 · PowerShell 검사 직렬화 또는 한 호출로 합치기 ·
**시간 초과와 진짜 실패를 구별해 확정 문구를 쓰지 않기**)은 보고서 4절에 있다.
이번에는 `installer/**` 를 건드리지 않았다.

**상승은 필요할 때 만들 수 없고, 이미 있어야 한다.**

### 2. 그래서 어떻게 했나 — 무인 설치 때 굽는다

무인 설치의 **첫 로그온**(`VBOXPOST.CMD`)은 아직 걸러지지 않은 전체 관리자 토큰으로 도는
유일한 순간이다. 그 한 순간에 `verify/vm/bake.ps1` 을 밀어 넣어 다음을 남긴다.

```text
① 표준 계정 2개   iristest · 테스트 사용자     (관리자 아님 — S03·S04 의 전제)
② 숨은 관리자     irisadmin                    (UAC 실험용)
③ UAC 값          ConsentPromptBehaviorAdmin=0 · LocalAccountTokenFilterPolicy=1
                  (EnableLUA 는 1 그대로 — 0 으로 내리면 그 PC 는 더 이상 보통 윈도가 아니다)
④ SYSTEM 대리인   작업 스케줄러 「IRIS-VM-Agent」 = C:\iris-vm\agent.ps1
                  C:\iris-vm\queue 를 1초마다 보고, 놓인 .job 을 SYSTEM 으로 실행
⑤ 흔적            C:\iris-vm\baked.json
SAC 는 건드리지 않는다 — S05 가 같은 ④ 통로로 스스로 켠다.
```

굽는 길은 `--post-install-template` 하나뿐이었다. `--post-install-command` 는 도움말 그대로
**"명령 한 줄"**(`A single command to run after the installation is completed`)뿐이라
수십 줄짜리 블록을 담지 못한다(7.2.16 도움말 실측). 그래서 Oracle 의 `win_postinstall.cmd` 에
블록 하나를 끼운 사본을 넘겼다.

그 사본은 보조 ISO 의 `VBOXPOST.CMD` 가 되어 **시스템 코드페이지로 읽히므로 순수 ASCII 여야 한다.**
한글이 든 `bake.ps1` 은 BOM 째 base64 로 싣고 손님 안에서 `certutil -f -decode` 가 되돌린다.
호스트에서 왕복 시험을 먼저 했다 — 되돌린 바이트가 원본과 **완전히 같았다**(13,270 바이트).

여기서 하나 배운 것(cmd 의 함정): base64 를 `echo` 로 파일에 적을 때 **괄호를 씌워야 한다.**
`echo abc1>>f` 에서 `1>` 는 **스트림 1번 리다이렉션**으로 읽혀 줄 끝 숫자가 조용히 사라진다.
`(echo abc1)>>f` 로 적는다. 비밀번호도 base64 로만 넘긴다(cmd 인용 규칙과 로그를 동시에 피한다).

### 3. 상승이 필요한 준비는 전부 이 통로로

```text
run.mjs ──> guest-elevate.ps1 (상승 없음)        손님 안, 걸러진 토큰
              │  C:\iris-vm\queue\<id>.job 쓰기 (임시 이름으로 쓴 뒤 rename)
              ↓
            IRIS-VM-Agent (SYSTEM, 이미 상승돼 있음)
              │  powershell -File <준비 스크립트> 실행
              ↓
            <id>.out · <id>.done  ──> guest-elevate.ps1 이 되읽어 그대로 출력
```

인자는 **base64** 로 넘긴다(`elevateArgs`). VBoxManage 가 `--` 뒤 인자 묶음을 지켜 주지 않아
공백이 든 인자는 손님 쪽에서 토막이 나기 때문이다(Task 23c ⑨와 같은 함정).
첫 줄에 `ELEVATE-CHANNEL baked|task` 가 찍혀 어느 문으로 갔는지 실행 로그에 남는다.

> 🔴 이 통로는 **일부러 만든 권한 상승 구멍**이다. 버리는 시험용 VM 안에만 존재하며,
> 설치기·배포물·이 개발 PC 어디에도 들어가지 않는다.

### 5. 죽은 무인 설치를 되살리는 법 (이번에 새로 안 것)

VM 한 벌을 80분 다시 만들지 않고 그 자리에서 고칠 수 있다.

