# IRIS 설치 패키지 설계 v2 (2026-09-15, 사용자 확정 조각 ①~⑩ 통합)

> 상태: **확정 설계**(사용자 검토·확정 완료 2026-09-15). 다음 산출물 = `docs\구현계획-v2.md`.
> 만든 사람: 함세준 · 허가서: MIT · 패키지 이름: IRIS · 판: **2.0.0**
> 전판 정본: `docs\설계.md`(v1, 2026-09-10) — 설치기 1층(준비·설치·로그인·Face 넘기기)의 결정 D1~D12는 아래 D2-xx가 바꾸지 않는 한 그대로 유효하다.

## 0. 한 줄 목표와 왜 v2인가

**목표 한 줄.** zip 하나를 풀어 두 번 클릭하면, 사람은 **구독 선택·작업 폴더 구성·구독 로그인** 세 가지만 하고 IRIS 체계 전체(실행기·에이전트·중계기·Face·메신저·도구·작업 폴더·지침·목록 카드)가 **에이전트 없이** 끝까지 설치·세팅된다. Face가 열리는 순간 이미 쓸 수 있는 상태다.

**왜 v2인가.** v1(1.x)은 2층 구조였다. 1층(설치기 화면)이 실행기·에이전트·중계기·Face를 깔고, 2층은 에이전트가 25,000줄 세팅가이드를 읽고 폴더·도구·카드를 세팅했다. 1층은 안정됐지만 2층이 계속 막혔다. 원인은 구조적이다.

1. **닭과 달걀** — 세팅 중인 세션은 자기가 켠 위험 권한을 소급받지 못해 허락 창을 계속 띄운다.
2. **하네스 차이** — 클로드·코덱스·판마다 훅·권한·선택 도구 동작이 달라 같은 가이드가 PC마다 다르게 굴러간다. 가이드 v7→v14의 대부분이 이 땜질이었다.
3. **비결정성** — 스크립트는 100번 같지만 에이전트는 매번 다르게 읽고 건너뛴다. "검사 18항목 통과"라는 보고조차 믿기 어렵다.
4. **가이드의 무게** — 25,251줄 중 약 23,600줄이 base64 파일 원문이다. 설치 패키지가 있는 지금은 파일을 그냥 동봉하면 된다.

세팅가이드 10단계를 성격별로 나누면 **에이전트의 판단이 필요한 단계는 하나도 없다.** 사용자 결정 3곳(구조·아이콘·메신저 로그인)은 이미 화면이 있고, 나머지는 전부 "순서대로 실행"이다. 그래서 v2는 **2층도 설치기가 한다.**

### 2-3. Face에서 에이전트가 하는 일 (확정)

**설치·세팅은 없다.** Face가 열리는 순간 영수증의 모든 단계가 `done`이어야 하며, 아니면 첫 인사 대신 안내 카드가 뜬다(코드로 보장). 에이전트의 첫 일은 `handoff.json`을 **읽고** 인사하는 것뿐이다. "영어 이름 비어 있는 폴더 채우기"는 제안일 뿐이고 사용자가 시키면 그때 하는 **첫 번째 평소 작업**이다.

## 4. 조각 ③ — 준비 검사와 실행 진입

### 4-1. 진입(SAC)

SAC(Smart App Control)가 켜진 PC는 MotW(웹 출처 표식)가 붙은 `.cmd`의 두 번 클릭을 실행 단추 없이 막는다. 근본 해결은 서명된 `.exe`(유료 인증서, 별도 결정). 이번 판은 **두 길 안내**를 홈페이지와 zip 안 `설치가 안 되면.txt`에 같은 원본으로 둔다: ⓐ zip 파일 속성 → "차단 해제" → 다시 풀기 ⓑ 탐색기 주소창에 `cmd /c IRIS-설치.cmd`. 설치기가 만드는 파일에는 표식이 없으므로 이후 단계는 SAC와 무관하다.

### 4-2. 검사표

| 검사 | 기준 | 실패 시 |
|---|---|---|
| zip을 풀었는가 | 임시 폴더 아님, `payload\manifest.json` 존재 | **막음** |
| 파일 무결성 | 전 부품 SHA-256 일치 | **막음** |
| 윈도 판 | 10 1809 이상 또는 11 | **막음** |
| CPU | x64 (ARM64·32비트 차단 유지) | **막음**, "지원하지 않는 CPU" 명시 |
| C 드라이브 | NTFS·쓰기 가능 | 값을 읽었는데 나쁘면 **막음**, 확인 자체가 안 되면 **경고**(진행 가능, 아래 단락) |

| 인터넷 | claude.ai·chatgpt.com·npm | **정보만**("로그인 단계에서 필요") |

결과는 영수증 `precheck`에 남겨 뒤 단계가 재검사 없이 읽는다. 로그는 `%LOCALAPPDATA%\IRIS-Installer\`에 남기고 영혼이 확정되면 `_agent\setup\`으로 사본. 실패 화면에는 로그 경로 복사 단추.

C 드라이브·디스크 여유·PowerShell 세 검사는 느린 PC에서 시간이 초과돼도 "막음"이 아니라 **"확인 못 함"**으로만 표시하고, 한 번은 시간을 2배로 늘려 자동으로 다시 시도한다(2026-09-15, Task 25 — 2vCPU VM에서 셋을 동시에 4초 안에 재던 예전 방식이 실제로는 정상인 PC를 "3GB 미만"·"5.1 이상 필요"라고 오판해 설치를 막았던 결함 수정). 사용자에게는 「다시 확인」 단추로 나타난다.

**"확인 못 함" = 경고(진행 가능), 막음이 아니다(2026-09-16, Task 26).** Task 25 이후에도 새 Win11 VM 세 대 모두 정확히 `ntfs-unknown` 하나에 걸려 설치가 영원히 멈추는 실측이 나왔다(재부팅 없이 처음 켠 이미지의 Storage 모듈이 WMI를 무겁게 초기화하며 `Get-Volume`을 콜드 스타트에서 느리게/실패하게 만드는 것으로 보임 — 확정은 아니고, VM 안에서 더 파고들 세션 시간이 없어 미확정). 그래서 ⓐ 디스크·NTFS 프로브를 `Get-Volume`(Storage 모듈)에서 `Get-CimInstance Win32_LogicalDisk`(WMI 직접, 모듈 로드·관리자 권한 불필요, 훨씬 가벼움)로 바꾸고, ⓑ `ntfs-unknown`·`disk-unknown`·`powershell-unknown` 세 상태를 **경고**로 낮췄다(`canProceed` = 막음이 0개일 때만이므로, 경고만 있으면 설치는 계속된다). 근거: PowerShell 5.1은 `bootstrap.ps1`이 이미 실행됐다는 사실 자체로 존재가 증명되고, 쓰기 가능 여부는 별도의 쓰기 프로브가 이미 지키고 있으며, 정말 NTFS가 아니거나 공간이 부족한 경우는 이후 압축 풀기 단계에서 분명한 오류 코드로 다시 드러난다. **성공적으로 값을 읽었는데 그 값이 나쁜 경우는 예전 그대로 막음**이다 — "확인 못 함"과 "확인했는데 나쁨"은 서로 다른 상태다.
