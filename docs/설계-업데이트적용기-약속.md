# 업데이트 적용기의 약속 — 창이 기대하는 것과 지금 적용기가 하는 것 (2.0.67 기준)

> 적용기 = IRIS 창이 꺼진 뒤 파일을 갈아 끼우는 바깥 프로그램(`updater\apply.mjs`, 설치된 PC 에서는 `<설치 폴더>\_agent\shared\tools\updater\apply.mjs`).
> 이 문서는 **지금 사실**을 적는다. 2.0.67 은 적용기와 설치기를 고치지 않았다 — 지금 동작을 굳히는 검사만 더했다(5절).
> 바꾸려는 것은 6절 「다음 설계에서」에 모았다. 창 쪽 원문 = 창 저장소 `daemon\update.mjs` · `daemon\update-chat.mjs`.

## 1. 한눈에

1. IRIS 안 「업데이트」는 **창이 받아 놓고 → 적용기가 넘겨받는** 두 걸음이다. 창이 적용기에 넘기는 인자는 계획 파일 경로 **하나뿐**이다.
2. 적용기가 **스스로 파일을 바꾸는 것은 "창만 바꾸는 계획"뿐**이다. 계획에 설치 패키지가 있으면 적용기는 새 zip 의 `IRIS-설치.cmd --auto` 를 띄우고 끝난다 — 실제 교체는 그 설치기가 한다.
3. 창(2.107.0)은 약속의 창 쪽 절반(고른 것 적기 · 능력 표 읽기 · 고친 파일 보관)을 이미 한다. **적용기 쪽 절반은 아직 없다** — 그래서 창의 「내 것 유지」는 잠겨 있고, 그 상태가 맞다(4절).
4. 설치 패키지 길에서 적용기가 결과 파일에 적는 `ok:true` 는 **"설치기에 넘겼다"** 는 뜻이다. "설치가 끝났다"가 아니다. 설치기는 끝난 뒤에도 그 파일을 다시 쓰지 않는다.

## 2. 길 둘 — 누가 파일을 바꾸는가

| 길 | 계획의 부품 | 파일을 바꾸는 것 | 적용기 자신이 새 판으로 바뀌는가 |
|---|---|---|---|
| 창만 | `face` | 적용기(`applyFaceItem` — 옛 폴더를 `.prev` 로, 새 폴더를 복사, `state` · `modules` 를 옮김) | 아니오 |
| 설치 패키지 | `package`(+ `face` 가 함께 있어도 건너뜀) | 새 zip 의 설치기(`installer\setup\unpack.mjs`) | 예 — 부품 `updater` 가 그때 새로 놓인다 |
| 새 zip 을 손으로 실행 | (계획 없음) | 새 zip 의 설치기 | 예 |

- 그래서 **지금 깔린 적용기는 한 판 늦다**: 2.0.66 을 깐 PC 가 2.0.67 을 받을 때 도는 적용기는 2.0.66 의 것이다. 새 약속을 적용기에 넣어도 그 약속이 처음 쓰이는 것은 그다음 업데이트다.
- 설치 패키지 길의 차례: 적용기가 계획을 읽음 → 데몬의 번호와 포트가 **둘 다** 사라질 때까지 기다림(최대 90초) → `cmd /c "<받아 둔 폴더>\package\IRIS-설치.cmd" --auto` 를 떼어 띄움(환경 변수 `IRIS_INSTALLER_AUTO=1` · `IRIS_INSTALLER_SOUL_NAME=<설치 폴더 이름>`) → 결과 파일을 쓰고 끝남 → 시작 파일이 `bootstrap.ps1` 을 부름(부품 지문 확인 · node 풀기 · 서버 띄우기 · 브라우저 열기) → 설치기 서버가 스스로 업데이트를 시작(`--auto` 자가 시작) → 끝나면 창을 다시 띄우고 스스로 종료.

## 3. 약속 표 — 창이 기대하는 것 ↔ 지금 적용기

| 약속 | 자리 | 창이 하는 것 | 지금 적용기 |
|---|---|---|---|
| 계획 `plan.json` | 받아 둔 폴더 `<설치 폴더>\_agent\shared\downloads\update-<YYYYMMDD-HHMMSS>\` | `{ schema:1, root, daemonPort, daemonPid, createdAt, items:[{ kind:'face'｜'package', dir, version }], relaunch:true }` 를 쓴다. 「지금 적용」 때 번호 · 포트를 다시 적는다. 고르지 않은 부품은 `items` 에서 뺀다 | 읽는다. `schema !== 1` 이면 아무것도 바꾸지 않고 `unsupported-schema`. `dir` 은 `_agent\shared\downloads` 아래만 받는다. 계획 파일을 고치지 않는다 |
| 인자 | 명령줄 | `<동봉 node> apply.mjs --plan <계획>` · 작업 폴더 = 적용기 폴더 | `--plan <경로>` 와 자리 인자 하나를 받는다. **모르는 인자는 오류로 끝난다** — 창은 새 인자를 넘기면 안 된다 |
| 고른 것 `choices.json` | 계획과 같은 폴더 | `{ schema:1, at, plan, parts, features, files:{ 경로: 'keep'｜'replace' }, backup }` 을 쓴다 | **읽지 않는다** |
| 능력 표 `capabilities.json` | 적용기 폴더 | `keepFiles === true` 하나만 본다. 없거나 못 읽으면 거짓 → 파일 선택을 잠그고 전부 "새 판으로" | **파일이 없다**(싣지 않는다 — 4절) |
| 고친 파일 보관 `update-kept` | `<설치 폴더>\_agent\setup\update-kept\<시각>\` | 적용 **전에** 고침 + 더함을 복사해 둔다(상한 1000개 · 파일 16MB · 합 256MB) | 모른다(읽지도 치우지도 않는다) |
| 새 기능 선택 | 창의 설정 | 적용기에 넘긴 직후 창이 적는다 | 할 일 없음 |
| 결과 `update-result.json` | `<설치 폴더>\_agent\setup\` | `at` 이 지난번 본 것보다 새로우면 한 번 읽어 알림을 띄운다(`items[].ok` 를 본다) · 기록장에 "계획한 판 = 설치된 판"을 대조한다 | 쓴다: `{ ok, items:[{ kind, version, ok, reason?, code?, message?, downloadUrl? }], at, relaunched, handedOffToInstaller? }`. **설치 패키지 길은 넘긴 직후의 값**(`ok:true · handedOffToInstaller:true · relaunched:false`)이고 설치기가 다시 쓰지 않는다 |
| 기록 `update.log` | `<설치 폴더>\_agent\setup\` | — | `apply start …` · `daemon gone after …` · `package: started … with IRIS_INSTALLER_AUTO=1 soul=…` · `apply done ok=…` |
| 받아 둔 폴더 치우기 | — | 결과를 읽은 뒤 계획 폴더를 지운다 · 7일 지난 `update-*` 를 치운다 | 창 폴더(`face\`)만 성공 뒤 지운다. 설치 패키지 폴더는 남긴다 |
| 창 다시 띄우기 | — | — | 창만 바꾸는 길 = 성공이든 실패든 한 번. 설치 패키지 길 = 넘기기가 **실패했을 때만**(성공하면 설치기가 띄운다) |

지금 적용기에 **없는 것**(코드로 확인): 선택 읽기 · 고친 파일 남기기 · 적용 잠금(`agent-update.lock` 을 쥐지 않는다) · 직전 재검증 · 단계 기록 · 창이 실제로 떴는지 확인 · 설치 패키지 길의 마지막 결과.

## 4. `keepFiles` 는 거짓 그대로

- 이 판(2.0.67)은 **능력 표를 싣지 않는다.** 창은 그 파일이 없으면 「내 것 유지」를 잠그고, 고친 파일은 `update-kept` 에 보관만 한다 — 2.0.65 부터 사용자에게 보이는 동작 그대로다.
- `keepFiles: true` 는 **고친 파일을 실제로 남기는 장치가 적용기(와 설치 패키지 길의 설치기)에 들어간 판만** 낸다. 장치 없이 이 값만 내면 창이 "남기겠다"고 약속한 파일이 통째 교체된다.
- 창은 계획의 부품 종류를 보지 않고 **지금 깔린 적용기의 표**를 본다. 설치 패키지를 고른 경우 실제 교체는 새 zip 의 설치기가 하므로, 표를 내는 판은 두 길 모두에서 남기는 장치가 돌아야 한다(6절).
- 검사: 업그레이드 게이트의 적용기 길이 "새로 깔린 적용기 폴더에 능력 표가 없거나 `keepFiles` 가 true 가 아니다"를 본다 · 단위 시험이 저장소에 `updater\capabilities.json` 이 없음을 본다.

## 5. 검사 — 적용기 길을 실제로 밟는다

`node verify/upgrade.mjs --via-applier`(= `npm run verify:upgrade-applier`). 업그레이드 게이트의 ② 를 "새 설치기를 `--auto` 로 직접 띄우기" 대신 아래로 바꿔 밟는다. ① 옛 판 설치와 ③ 판정(ⓑ ~ ⓜ)은 직접 길과 같은 코드다.

```text
① 옛 판을 연습 루트에 설치                      (직접 길과 같다)
    ↓
②ⓐ 새 zip 을 창이 받아 두는 자리에 푼다          <연습 루트>\_agent\shared\downloads\update-<시각>\package
    ↓
②ⓑ 창이 쓰는 꼴 그대로의 계획(plan.json)을 쓴다   설치 패키지 한 부품
    ↓
②ⓒ ① 이 깐 **옛 판의 적용기**를 창처럼 띄운다     옛 판의 동봉 node · apply.mjs --plan <계획>
    ↓
②ⓓ 적용기 → IRIS-설치.cmd --auto → bootstrap.ps1 → 설치기 서버가 스스로 업데이트
    ↓
③ 판정                                          직접 길의 ⓑ ~ ⓜ + 적용기 길의 ⓝ
```

적용기 길에서만 보는 판정(ⓝ — `verify\upgrade-applier.mjs`, 단위 시험 `tests\upgrade-applier.test.mjs`):

| 판정 | 보는 것 |
|---|---|
| 넘김 | 적용기가 종료 코드 0 · 결과 파일에 설치 패키지 한 줄(계획의 판) · 적용기가 낸 글 = 결과 파일 |
| 「지금 동작」 넘김 = 완료 아님 | 결과가 `ok:true · handedOffToInstaller:true · relaunched:false` · 적용기가 끝난 그때 영수증은 아직 옛 판 · 결과의 시각이 설치기가 끝나기 전 |
| 「지금 동작」 설치기는 결과를 다시 쓰지 않는다 | 설치기가 끝난 뒤의 결과 파일이 적용기가 쓴 그대로 |
| 기록 | `update.log` 에 계획 읽기 → 데몬 확인 → 시작 파일 띄우기(이 설치 폴더의 이름) → `ok=true` 가 차례대로 |
| 시작 파일 | `bootstrap.ps1` 이 새 판의 설치기 서버를 띄웠다 |
| 무접촉 | 계획 파일이 그대로 · 받아 둔 설치 패키지 폴더가 남아 있다 |
| 「내 것 유지」 잠김 | 새로 깔린 적용기에 능력 표가 없거나 `keepFiles` 가 true 가 아니다 |

**「지금 동작」이라고 적힌 판정을 바꾸는 법.** 그 줄들은 "이대로가 좋다"가 아니라 "지금 이렇다"를 굳힌 것이다. 적용기나 설치기의 그 동작을 고치는 판은 ① 6절의 해당 항목을 설계하고 ② `verify\upgrade-applier.mjs` 의 그 판정과 `tests\upgrade-applier.test.mjs` 의 짝을 **같은 커밋에서** 새 동작에 맞게 고치고 ③ 이 문서 3절 표의 "지금 적용기" 칸을 고친다. 판정만 지우거나, 코드만 고쳐 게이트가 실패한 채 두지 않는다.

게이트가 실제 PC 와 다른 점(연습이라 일부러):

- 계획의 `daemonPid` · `daemonPort` = 이미 끝난 번호 · 닫힌 포트(창이 없으므로). `relaunch` = false(창은 true) — 넘기기가 실패해도 연습 루트의 IRIS 창을 진짜로 띄우지 않게. 넘기기가 성공하면 적용기는 이 칸을 쓰지 않는다.
- 시작 파일은 브라우저를 연다. 게이트는 **받아 둔 사본**의 `bootstrap.ps1` 에서 그 한 줄만 끈다(zip 과 저장소의 원본은 그대로 · 서버 띄우기 · 지문 확인 · node 풀기는 원본).
- 설치기는 연습 환경으로 돈다(사용자 환경 변수 무접촉 · 오프라인 · 창 다시 열기 끔 · 상태 폴더 우회). 이 값들은 환경 변수로 적용기 → 시작 파일 → 서버까지 물려 내려간다.
- 창이 하는 일(서명 · 지문 확인 뒤에 풀기, 고르기, `choices.json`, 보관)은 게이트가 하지 않는다 — 그것은 창의 검사 몫이다.

**상태(2.0.67):** 게이트의 이 길은 코드만 들어갔고 **아직 한 번도 돌지 않았다.** 조각은 단위 시험이 본다(계획이 창 소스의 글자와 같은가 · 저장소의 적용기를 진짜로 띄워 가짜 시작 파일까지 넘어가는가 · 판정이 양쪽으로 맞는가). 첫 실행에서 볼 것: 연습 환경 변수가 `bootstrap.ps1` 을 거쳐 서버까지 닿는가 · 지문 확인과 node 풀기에 걸리는 시간이 기다리는 한도(서버가 뜰 때까지 10분) 안인가 · 끝난 뒤 남는 프로세스가 없는가.

## 6. 다음 설계에서 — 코덱스가 짚은 빈틈

2026-11-27 설계 검토(D09 `최신판 배포-3차-코덱스검토-설계 초안…`)가 「내 것 유지」 · 잠금 · 결과 기록 초안에서 **막아야 한다**고 짚은 것이다. 3차 설계 정본이 "일곱"이라고 적은 것 — 검토 표의 여섯 줄이고, 잠금 줄에 두 가지가 들어 있다. 이 일곱이 풀리기 전에는 그 기능을 싣지 않는다.

| # | 빈틈 | 왜 문제인가 | 검토가 준 방향 |
|---|---|---|---|
| 1 | **결과 기록 경쟁** | 설치기를 먼저 띄우고 적용기가 결과를 쓰면, 빨리 끝난 설치기의 마지막 결과를 적용기의 늦은 중간 결과가 덮을 수 있다. 옛 적용기도 이 경쟁에 낀다 | 띄우기 **전에** 인계 기록을 남기고, 마지막 결과는 작업 식별자별 **다른 파일**에. 마지막 기록을 중간 기록으로 덮지 않는다 |
| 2 | **선택이 깨졌을 때 사용자의 뜻이 조용히 사라짐** | 「내 것 유지」를 골랐는데 선택 파일이 깨지거나 계획과 어긋나면 전부 새 판으로 바뀐다 | "선택 없음"과 "선택 손상 · 불일치"를 가른다. 뒤쪽은 적용을 멈추고 다시 보게 한다 |
| 3 | **잠금을 시간으로 빼앗음** | 30분이 지났다는 것만으로 살아 있는 작업의 잠금을 넘겨받는다 | 원자적으로 쥐고, 임자 식별자와 살아 있는지를 본다. 시간만으로 넘겨받지 않는다 |
| 4 | **잠금 인계의 빈틈** | 적용기가 잠금을 놓고 설치기가 쥐기 전에 다른 업데이트가 들어올 수 있다 | 소유권을 넘겨준다. 설치기가 못 쥐면 아무것도 바꾸지 않고 끝난다 |
| 5 | **자료를 옮기는 도중의 복구** | `state` 일부가 이미 새 폴더로 옮겨진 뒤 끊기면, 옛 폴더만 되돌린 창은 그 자료를 못 찾는다. `node_modules` 도 이미 옮겨졌을 수 있다 | 폴더마다 옮기기 전 · 후를 적고 `state` · `modules` · 의존성 각각의 실제 자리를 보고 되돌린다. 단계 사이뿐 아니라 **옮기는 도중**의 끊김을 시험한다 |
| 6 | **창이 안 뜨는 까닭을 단정함** | 응답이 늦은 것을 남긴 파일 탓으로 보고 도는 중인 파일을 다시 바꿀 수 있다. 새 판에 없던 더한 파일은 되돌릴 원본도 없다 | 응답 실패만으로 단정하지 않는다. 다시 바꾸기 전에 그 프로세스가 끝났는지 확인하고, 더한 파일은 지우지 않고 따로 보관한다. 끝나지 않은 작업의 복구 자료는 청소하지 않는다 |
| 7 | **배포 도구의 두 묶음 대조** | 설치 패키지 속 창에 파일 목록 · 서명을 실으면, 지금 배포 도구(이 저장소 밖)가 그 두 파일을 오류로 본다 | 배포 도구를 **같은 변경**에 넣는다: 양쪽에 있고 바이트가 같아야 통과, 금지 파일 검사는 그대로 |

같은 검토의 "고치면 좋음" · "참고"(막는 것은 아니지만 설계에 들어가야 할 것):

- 설치 속 창에는 `node_modules` 가 있고 창 따로 묶음의 서명 목록에는 없다 — 설치용 대조에서 그 범위를 뺀다고 적는다.
- zip 의 지문이 맞아도 실제로 실행하는 **푼 폴더의 `installer\` 와 시작 파일**은 바뀌었을 수 있다 — 실행 파일까지 zip 과 대조하거나, 확인한 zip 을 새 임시 자리에 푼다. "설치기 전체 재검증"이라고 부르지 않는다.
- 계획의 판 번호는 올리지 않는다(`schema:1` 유지 · 곁 파일로 넓힌다) — 옛 적용기는 모르는 판에 멈춘다. 새 칸이 없어도 옛 뜻이 그대로여야 하고, 능력 표는 **실제로 도는 적용기**와 맞아야 한다.
- 최신판도 받는 시험 열쇠: "열쇠 없는 PC 는 안정판"이라고 말한다(열쇠가 복사된 PC 는 받는다). 미러 창구의 허용 이름을 먼저 넓혀야 하고, 목록에서 판을 고를 때 지금보다 낮은 판으로 내려가지 않게 한다.
- "설치기 길은 적용기를 쓰지 않는다"는 말은 틀리다 — 적용기가 설치기에 넘기고, 교체를 설치기가 한다(2절).

이 판에서 일부러 하지 않은 것: 적용기 본체의 동작 변경 · `choices.json` 읽기 · 「내 것 유지」 · 적용 잠금 · 되돌리기 · 설치기가 마지막 결과를 쓰기 · 창 묶음에 파일 목록과 서명 · 시험 열쇠 · 창(IRIS-Face) 변경.
